How to Size Your LLM Rate-Limit Budget (and Avoid 429 in Production)

A repeatable six-step method to find which limit binds first, how much headroom to leave, and why caching can lift your effective ceiling on Anthropic but not OpenAI.

The method

  1. Compute usage per dimension. Let R = requests/min, Ti = avg input tokens/req, To = avg output tokens/req.
    • Anthropic: RPM usage = R, ITPM usage = R × Ti, OTPM usage = R × To (three independent ceilings).
    • OpenAI: RPM usage = R, TPM usage = R × (Ti + To) (input and output share one combined limit).
  2. Find utilization. For every dimension, utilization = usage ÷ limit. This normalizes RPM and token limits onto the same 0-100% scale so they are comparable.
  3. Identify what binds first. The dimension with the highest utilization is your bottleneck — it 429s first as you scale. Optimizing anything else is wasted effort until this one stops being the max.
  4. Leave headroom. Target under 70-80% utilization on the binding dimension at expected peak. Real traffic is bursty; a dimension at 95% on a per-minute average is already failing per-second bursts.
  5. Smooth per-second bursts. "Per minute" is enforced ~per second. A burst above ceil(RPM ÷ 60) requests in any single second 429s even under the per-minute cap. Add a client-side limiter sized to the per-second figure.
  6. Use caching to lift effective ITPM (Anthropic only). Anthropic cache reads do not count toward ITPM, so caching a large stable prefix raises your real ITPM ceiling with no tier change. On OpenAI this does not work — cached tokens still count toward TPM.

Worked example

Sonnet 4.6, Tier 4 (RPM 4,000 / ITPM 2,000,000 / OTPM 400,000), at R = 1,000, Ti = 3,000, To = 600:

DimensionUsage / minLimit / minUtilization
RPM1,0004,00025%
ITPM3,000,0002,000,000150% — binds, 429
OTPM600,000400,000150%

RPM looks comfortable at 25%, but ITPM is at 150% — this workload 429s on input tokens immediately. The fix is not a higher RPM tier; it is caching the stable prefix (drops billed ITPM), trimming input, or moving to Tier 4's higher per-model ITPM. Sizing on RPM alone would have shipped a broken service.

The 4-dimension OpenAI caution: OpenAI also enforces RPD and TPD (per-day) on top of RPM/TPM. A job that passes per-minute checks all day can still 429 on the daily ceiling late in a run. Include RPD/TPD in step 1 if you run sustained batch traffic.

FAQ

How do I calculate token usage per minute?
Anthropic: ITPM = R×Ti, OTPM = R×To. OpenAI: TPM = R×(Ti+To) (combined). R is requests/min.
Which rate limit binds first?
The dimension with the highest usage ÷ limit ratio. That is the only bottleneck worth optimizing until it stops being the max.
How much headroom should I leave?
Under 70-80% on the binding dimension at peak. Per-second quantization means a 95% per-minute average is already bursting into 429s.
Does caching help with rate limits?
On Anthropic yes — cache reads are excluded from ITPM. On OpenAI no — cached tokens still count toward TPM.
